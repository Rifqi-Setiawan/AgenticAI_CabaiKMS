## 2. Raw field samples — `data/samples/`

Only **one** file currently exists: `data_input.xlsx`. It has exactly one
sheet, `Resume Data` (used range effectively `A1:N15`; columns `O`–`Z` are
entirely empty despite the sheet's nominal `A1:Z1000` dimensions).

### 2.1 Variant classification

This file is **variant (ii): row-oriented**, one row = one observation
("Lokasi ke-1" … "Lokasi ke-13"), with the varietas identity carried in an
anchor column, `Jenis Cabai` (column F). This matches the row-oriented
pattern described in the brief; anchor detection (finding the "jenis cabai"
column, since its position isn't fixed at F in general) will be required to
parse files shaped like this.

**No *real* sample file for variant (i) (transposed, varietas-as-column-headers)
exists in `data/samples/`.** The canonical template itself happens to be laid
out that way, but it is the clean target schema, not a messy raw-field
example — it shouldn't be used to validate transposed-variant parsing logic.

Per the user (`docs/OPEN_QUESTIONS.md` Q1), a fabricated stand-in was created
instead of waiting for a real one:
[`data/samples/sample_transposed_sintetis.xlsx`](../data/samples/sample_transposed_sintetis.xlsx).
It's generated from a subset of the canonical template's own row labels
(read dynamically from the template, not hand-typed) across all domains,
with deliberately injected messy notations — decimal-comma range
(`"10,5 - 14 cm"`), no-space range (`"8-10cm"`), an approx-symbol range
(`"±12 cm"`), natural-language color instead of an RHS code (`"hijau tua"`),
`;`-joined multi-value, a stray `*` footnote marker, a bare `-` for
"missing", trailing whitespace, inconsistent capitalization, and a leading
title/description row sitting above the real header row (to exercise
header-row detection, not just value parsing). Its own first two rows say
plainly that it's synthetic. Treat it as a mechanical parser exercise, not
as evidence of what real variant-(i) messiness looks like — swap it out if
a real transposed-format file ever turns up.

### 2.2 Structure

- **Two-row hierarchical header:** row 1 has section labels merged across
  several columns (`Data Koordinat`, `Mean (Rerata) Data Fisiologi Tanaman...`,
  `Data ekologi tanah`, `Data microclimate`); row 2 has the actual field
  names (`S`, `E`, `Chlorophyll Content (SPAD)`, `Nitrogen content (mg/g)`,
  `Humidity (%)`, `Suhu permukaan daun(oC)`, `Kelembaban tanah (%)`, `pH
  tanah`, `Suhu udara (0C)`, `Kelembaban udara (%)`). Real data starts row 3.
- **Columns present:** No | Lokasi Sampling | Data Koordinat (S, E) |
  Ketinggian Lahan Sampling (mdpl) | Jenis Cabai | 4 physiology columns | 2
  soil-ecology columns | 2 microclimate columns.
- **13 data rows**, one per sampling location.

### 2.3 Example messy-value notations found

- **Ranges as text:** `"28.3 - 30.5"` (Suhu udara), `"72 - 67"` (Kelembaban
  udara, descending order — day/night swing recorded as a range).
- **Inconsistent single-value vs. range for the same conceptual field:**
  Kelembaban udara is `"72 - 67"` for one location but a plain int `78` for
  another and `56` for a third — same column, mixed representation.
- **Species/Latin-binomial naming in the varietas anchor column:** `"Cabai
  rawit (Capsicum frutescens L)"`, `"cabai besar (Capsicum annum L)"`
  (inconsistent capitalization of "cabai" too). **None of these strings
  match any of the 10 varietas names used as column headers in the
  canonical template** (Gendot, Kopay, Katokkon, …). See
  `docs/OPEN_QUESTIONS.md` Q2 — this is a real mapping gap, not just a
  formatting one.
- **No decimal-comma values observed in this particular file** (unlike the
  canonical template) — its numeric fields are stored as native floats with
  dot decimals. Decimal-comma is a "messy canonical value" pattern, not
  (so far) a "messy raw sample" pattern; both should still be handled by any
  normalization logic since gold data has it.

### 2.4 Content coverage gap vs. the canonical schema

This sample's fields map only to canonical row 56 (`Lokasi`) — and even that
is a **multi-field-to-one-cell** problem: the source has a location name, a
lat/long pair, and an elevation, but the canonical template has a single
`Lokasi` cell per varietas. See `docs/OPEN_QUESTIONS.md` Q3.

The rest of the sample's fields (chlorophyll content, nitrogen content, leaf
surface humidity/temperature, soil humidity/pH, air temperature/humidity)
have **no corresponding row anywhere in the canonical template** — this
sample carries zero morphological (habitus/daun/bunga/buah/biji) data. That
may simply mean this particular file isn't a good exercise case for the
morphological-extraction agent, but it's worth confirming since it's the
only sample currently available.
